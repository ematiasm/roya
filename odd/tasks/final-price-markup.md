# Set a product's final price and let the markup follow

## Objective

Let an operator type a product's final, tax-inclusive price and have the system solve for the net price and rewrite the markup, so the ladder keeps showing a coherent cost → markup → net → tax → final chain.

## Problem

The pricing chain is one-directional today: cost and markup derive the net, taxes derive the final price. There is no way to express the opposite intent — "this product should sell at 100 including tax" — so the operator has to mentally invert a calculation that includes per-tax rounding.

That inversion is not a formula. The final price is `round(2, net + Σ round(2, net × rateᵢ/100))`, so each tax is rounded on its own. Dividing the target by `1 + Σrates/100` lands within a cent or two of the right answer often enough to be useless: the operator types 100 and the ladder shows 100.01, which is a lie about what they asked for.

## Decisions

- **One-shot conversion, not a pricing mode.** The stored net stays canonical, no schema change and no migration, and document lines are unaffected — they snapshot the net exactly as they do today. Changing a tax later still moves the final price, which is the already-documented consequence of the net being the truth.
- **The solve is a bounded search, not a division.** An initial estimate places the window; a small cent-range search then finds a net whose final price is **exactly** the typed value. A division alone cannot guarantee that with per-contribution rounding.
- **Tie-break by proximity to the estimate.** More than one net can produce the same final price. The one closest to the unrounded estimate is chosen, because it is the one that best represents the operator's intent. The rule is stated where the choice is made, with the evidence, not as "whichever the loop finds first".
- **The markup round trip is verified, not assumed.** After solving the markup the real deriver is run again and compared. If it does not reproduce the solved net, precision is increased and the attempt retried, up to a bound. If it never closes, the request is refused with a typed message rather than storing a price that is not the one asked for.
- **Zero cost derives no markup, and says so.** A manual product with no cost can have its final price set — the net is solved and no markup is invented — and the ladder states the markup is not derivable without a cost. A product that already carries a markup and has no positive cost is refused, because the stored markup and the stored net would contradict each other and the next save would silently undo the change.
- **A manual product becomes markup-managed.** Setting a final price writes `markup_pct`, which is what "the markup updates automatically" means; a manual product that gets a final price is no longer manual, and the ladder says so.
- **One control, its own route.** The final price is a separate small form beside the ladder, not another field in the main save form, because it means something different: the save form expresses cost and markup, this expresses the price the customer pays. It follows the same pattern as the existing cost-recording control.
- **U2, REVISED: PREVIEW, THEN CONFIRM.** The maintainer chose the third option, and the design question it answers is closed. The operator must see the consequence before it is committed. Two endpoints, and the split is structural rather than cosmetic: `GET /web/product-final-price` is the preview and `POST /web/product-final-price/confirm` is the write. The preview is a **GET** for the same reason the ladder preview is — "it persists nothing" has to be a property of the route, and a path with no write verb has none; a POST to it is 405 and a GET on the confirm is 405, so each step is reachable by exactly one verb. The confirm is gated `inventory.write`; the preview is `inventory.read`, because a preview writes nothing.
- **U2: the confirm RE-SOLVES and never stores what the preview showed.** This is the rule that makes the two steps safe, and it is the whole safety argument: the preview is **advisory**. It is not a proposal the server holds, not a token, and there is no path by which its output reaches the write. The confirm is handed **values** and runs the same pure solve through the same shared call the preview made. So a **stale preview can mislead an operator's expectation — a UI defect they can see — but it can never reach the row**, because the row is computed from the values the confirm carries. The resolution is pinned by a test and it is the safe direction: the confirm's values always win. Storing the previewed pair would be the direction that corrupts — a stored net beside a stored markup that does not reproduce it is a self-contradicting row, and the next ordinary save would silently undo the conversion. Concretely: preview `100.00` against a cost of 10 (markup `809.10`), then change the cost to 20 and confirm; what is stored is markup `354.55`, because `809.10%` of 20 derives `181.82`, twice the solved net.
- **U2: the conversion is solved against the cost ON SCREEN, and confirming persists it.** The preview answers "what would happen if I saved what is on screen right now", which is the only useful question to answer, and a cost typed and not saved is exactly the case an operator most needs previewed. The control therefore **reads the save form's own `cost_price`** through `hx-include="#product-edit-form"` — one owner, many readers, never a second editor of the same field. It deliberately does **not** read the save form's `markup_pct`: the markup is an OUTPUT, a final price *determines* it, and reading a typed markup would let it override the one the solve verified. So one `UPDATE` writes `cost_price`, `sale_price` and `markup_pct` together, and the operator is told that in the confirm control's own help line *before the button exists*. The cost travels with the pair because a net derived from a cost the database does not hold is a price nobody can re-derive. The solve is still handed the product's STORED markup, for its contradiction rule alone.
- **U2: the confirm control does not exist until a preview has succeeded.** It is not in the drawer's markup at all — the server renders it into `#product-final-price-confirm` out of band — so "preview, then confirm" is a property of the markup and not a disabled attribute somebody can work around with the keyboard. A refused preview empties the slot; so does a refused confirm. The control's own form `hx-get`s the preview, so a stray Enter can only ever preview.
- **The ladder shows the truth after the conversion.** If the markup was rounded on the way, the ladder says the derived price is the stored net's consequence, not a second free number.
- **Unreachable targets are refused, never approximated.** A final price so small that no net produces it is a typed refusal, not a silently different price.
- **A refusal in EITHER step is answered with the ladder fragment and nothing else.** Not an error page and not the drawer body: the same `ProductPriceLadder` fragment, the same `ladder_refusal_message`, the same one `price_refusal_key` mapping, the same sentence in the operator's language, through the same `LadderInput::Refused` the ladder already uses. The control targets `#product-price-ladder`, so a refusal renders where a ladder refusal has always rendered and the drawer body — the save form, its unsaved values, the control itself — is never replaced. Swapping the body on a refusal would silently discard unsaved work on a product that is perfectly storable, which is the one thing a refusal must never do. A refusal in a preview is the NORMAL answer to an impossible target, not an error state.
- **A price that is not a number is a form error, not a refusal.** 400 in both steps, the answer the ladder's own `Unreadable` state and the cost control already give. A `PriceRefusal` is a sentence in the catalog, and a catalog sentence no rule can produce is a lie an operator would have to read.
- **The markup-is-not-derivable note lives in the ladder, and it is a NEW sentence rather than a new refusal.** "No positive cost ⇒ no markup" is not a price the save path refuses — it is a *successful* conversion that stores a net and no markup. It is stated in the ladder's own vocabulary (`ProductLadderNoCostMarkup`), beside the row it explains.
- **The preview needs no renderer of its own.** The solved net and the solved markup are handed to `LadderInput::Form` — the input the save form's own preview already uses — so the ladder re-derives the net from that cost and that markup through `derive_net_sale_price` and re-totals it through `calculate_line_taxes`. A preview therefore re-verifies the solve's round trip on every keystroke, and its published total is the typed figure or the preview is wrong about something the ladder itself would show. `from_form` comes out true, so every row is chipped "Unsaved", which is what a preview is.
- Technical artifacts, code, comments, tests, and UI copy are English.

## Scope

### In scope

- A pure, total solve: final price → net price, and net price → markup, with a verified round trip.
- Typed refusals for every state the solve cannot honour, rendered through the existing single refusal renderer.
- One route and one ladder control, gated `InventoryWrite`, read-only in effect: the preview never persists.
- The conversion write, which rewrites net and markup in one transaction and re-renders the drawer.
- Focused tests plus a Playwright test that types a final price and reads the resulting ladder.

### Out of scope

- Any schema change or migration.
- Any change to sale or purchase document math, the tax snapshot contract, or the net-is-canonical decision.
- A JSON API twin for the conversion route; recorded as a deliberate omission, since the request is about the product screen and an unwritten API surface is better than a written one nobody asked for.
- Locking the final price against later tax changes.

## Authorized scope

Repository-local service, route, template, localization, test, and feature-document changes. No push, PR creation, or merge without explicit user request. No database reset, no migration, and no change to the development database.

## Route declaration

Two bounded delegated-direct ODD work units. U1 is the arithmetic and is deliberately separated from the wiring, because it is the part that can be silently wrong: a solve that returns 100.01 for a typed 100 looks exactly like a correct one in a screenshot. One writer per unit. The parent owns task closure, commits, verification, and delivery reporting. No SDD phase is created.

## Acceptance criteria

1. Typing a final price yields a stored net whose derived final price is exactly the typed value, for zero, one and several taxes.
2. The markup is rewritten and re-deriving from it reproduces the stored net.
3. A case where a naive division misses by a cent is covered by a test, and the solve lands on the typed value.
4. More than one valid net is resolved by the documented tie-break, not by loop order.
5. A target no net can produce is refused with a typed, localized message and nothing is written.
6. A manual product with a cost becomes markup-managed, and the ladder says so.
7. A product with no cost takes a final price without inventing a markup, and the ladder states the markup is not derivable.
8. A product that already has a markup and no positive cost is refused, with nothing written.
9. The preview persists nothing; the conversion write is atomic and audited like every other product mutation.
10. Documents are unaffected: a new line still snapshots the net, and existing lines never move.
11. Focused tests, the full Rust suite, and the applicable browser checks pass, with every skip recorded.

### Verification findings, fixed (2026-09-27)

Four findings. Three were real defects against the feature's OWN stated principle, and they are fixed by mechanism rather than by a promise.

- **M1 — a successful confirm used to destroy unsaved work.** It re-rendered `#product-drawer-body` wholesale, which put the stored values back into `sku`, `name`, `kind`, `category_id`, `unit`, `track_stock`, `min_stock`, `max_stock`, `location` and `notes` and lost everything the operator had typed there. The refusal path deliberately preserved that work and the document says a refusal must never discard it; a SUCCESS discarding the same work was the same defect wearing a better outcome. **The rule now, and the shape chosen for it:** the answer re-renders **exactly the regions that are FUNCTIONS of the three fields the confirm wrote, and nothing else** — the three price fields, the script that binds two of them, the stale-cost badge (its verdict is the stored cost against the supplier's reference cost) and the audit line (a conversion is a product update, so `updated_by` moved). Each renders from the SAME partial the drawer includes, so the confirm cannot drift from the drawer it refreshes. A confirmed conversion therefore leaves the ladder showing the truth and every other typed field exactly as typed and still editable. `a_confirmed_final_price_does_not_re_render_the_save_form_it_did_not_write` and `a_refused_final_price_confirm_keeps_every_unsaved_field_too` pin the mechanism on both paths, and the e2e pins the browser outcome by typing into `location`, `notes` and `min_stock`, confirming, and asserting all three are still on screen and still editable.
- **M2 — the confirm outlived its own preview.** The save form's four ladder inputs all refresh `#product-price-ladder` from `/web/product-price-ladder`, and that endpoint returned only the ladder, so a confirm survived every save-form refresh: preview a final price, edit the cost, and an ENABLED confirm sat under a ladder that was now previewing the save form. The stored row stayed correct — the confirm re-solves — but the visible promise was wrong. **How the two callers are told apart: they do not share an endpoint, so there is no flag to get wrong.** `/web/product-price-ladder` is the SAVE FORM's preview and `/web/product-final-price` is the conversion's, and every answer from the first one now emits an out-of-band clear of `#product-final-price-confirm`. It is unconditional, including on a bare read, because any answer from that path is a statement about the form and the confirm's premise is gone either way; the only way to get a confirm back is to run a final-price preview. Pinned in Rust by `a_save_form_ladder_refresh_retires_a_final_price_confirm_it_invalidated` (which also asserts the final-price preview still INSTALLS the confirm) and in the browser by `test_editing_a_price_field_in_the_drawer_retires_the_final_price_confirm`, which walks the operator's real sequence and asserts the confirm is gone and unreachable.
- **M3 — the typed sale price was silently overwritten.** The help line explained that the markup is not read and that the solve uses the cost, and said nothing about `sale_price`. It now says, in both languages, that a final price replaces both the net price and the markup, that **the sale price and the markup in the form are not read**, that what is typed there is kept for the ordinary save, and that a confirmed final price overwrites it. The claim is pinned against the CODE, not just the copy: `a_final_price_confirm_ignores_a_sale_price_in_the_request_body` sends `sale_price=999.99` in the body and asserts the stored net is the solved `90.91` — `FinalPriceValues` has no `sale_price` field, and a `FinalPriceValues` that grew one would store 999.99 and fail.

(b) The bilingual refusal loop previously reached only the PREVIEW, so "at BOTH steps, in EN and ES" was an overclaim; the loop now runs the **preview and the confirm** in each language and asserts the sentence and a byte-identical row for all four answers. (c) The handler's `confirmable: false` on a refused confirm had no test, and an unasserted comment is a lie waiting for a refactor — three tests now assert no confirm is on offer on a refused preview, a refused confirm (EN and ES), and a refused out-of-range confirm. (d) The no-cost note in `product_price_ladder.html` sits **deliberately outside** the `net_refusal` guard, and the template now says so with the reason: a refused ladder still shows a markup row that is a dash, so the note that explains the dash is as needed on a refusal as on a success; the note is a sentence about a column, not a figure, so the no-money guarantee is untouched. `a_refused_final_price_preview_of_a_no_cost_product_states_both_facts_and_no_money` pins all three facts together.

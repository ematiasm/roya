{# Purchase return record body. Rendered both by `/purchase-returns/{id}` inside the shell and standalone by every action response that swaps `#purchase-return-record`, so the same context travels with the fragment either way. The status gate below is presentation only: the service stays the authority and refuses edits to a confirmed return. THE LINE EDITOR, and decision 1 of the design expressed as markup. A return line names a PARENT purchase line and carries no product of its own — `PurchaseReturnLine` stores no `product_id` on purpose, so the product, the quantity bought and the frozen cost are all read THROUGH the parent line. That is why every row here is a parent line: it shows what was bought, how much of it confirmed returns already took, what is still returnable, and the frozen unit cost. **AND THERE IS NO PRICE INPUT ANYWHERE IN THIS FILE.** Not a hidden one, not a disabled one, not a readonly one. The cost is RENDERED AS TEXT in its own column and the only control on the row is the quantity. A disabled input would still be an input: the next person to touch this template would re-enable it, and the service would then silently ignore it, because `add_line` and `update_line` have no price parameter at all. `a_draft_purchase_return_renders_with_no_price_input` asserts on the rendered HTML, so a price field added here fails the suite rather than the design. #}

{# The record shell's interactions. It lives in the PAGE SHELL, not in the record fragment: the fragment is swapped by every action response, and a script inside swapped content would re-register the document-level listeners on every swap. #} {# THE COUNTER FLOW. An operator at a counter types a quantity per row twenty times in a row — take a row, type a quantity, commit, take the next — and the commit is a blur, because htmx's trigger for the quantity control is `change`. So the flow is twenty tab-and-click round trips through a mouse, for a job that is one keystroke each, and nothing on the page says a row is a step in a sequence at all. **It lives in the PAGE SHELL for the reason the block above states**, and it is the purchase-return shell's block with this family's ids: the two families mirror each other, so a difference here is a difference both screens would have to grow. **Every destination is an ID STRING, never an element reference.** A commit replaces the money region (`hx-swap="outerHTML"`), so the input that was typed into and the input the operator should land on are both destroyed and rebuilt by it. A reference taken before the swap would point at a detached node, which accepts `.focus()` and does nothing at all. **The swap is observed, never waited for.** htmx raises `beforeRequest` when a request is actually issued and `afterSettle` when the rebuild has finished; a blur dispatches `change` synchronously, so the two are the boundary between "this commit is in flight" and "this commit has landed". No timer is involved, and a keystroke that changes nothing raises no request at all — measured against the vendored htmx 1.9.12, which skips an unchanged `change` — so the two events are the only honest signal that a rebuild is or is not coming. #} {% endblock %}
